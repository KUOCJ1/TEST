## 驗證標準與推進機制

每個 Sprint 是否「完成、可以往下一個推進」，一律用以下**共同關卡（Gate）**加上
該 Sprint 自己的**功能驗收表**共同判定。兩者都通過才算過關；任一項不過，
該 Sprint 視為未完成，不推進到下一個。

### 共同關卡（每個 Sprint 都要過，缺一不可）

| # | 檢查 | 通過標準 | 指令 |
|---|---|---|---|
| G1 | 前端單元/元件測試 | 全綠，且新增/變更的行為有對應測試（不是只維持原有測試通過） | `npm test` |
| G2 | 後端 API 測試 | 全綠 | `cd server && npm test` |
| G3 | Lint | 0 problems | `npm run lint` |
| G4 | Production build | 成功產出 `dist/`，無 build 期錯誤 | `npm run build` |
| G5 | 後端可正常啟動並回應健康檢查 | `{"ok":true}` | 見下方「本機驗證環境」 |
| G6 | 冒煙測試（Smoke） | 該 Sprint 涉及的畫面至少手動或以 Playwright 跑過一次黃金路徑，無 console error、無明顯版面錯亂（含手機寬度 375px 與深色模式各看一次） | 見各 Sprint 的「冒煙腳本」 |
| G7 | Git 狀態 | 變更已 commit 並 `git push` 到 `claude/ai-assessment-survey-4vhjun`；GitHub Actions `deploy.yml` 綠燈 | `git push` + 確認 PR #7 的 check run 狀態 |
| G8 | 文件同步 | 若該 Sprint 影響架構、API 或使用者操作流程，`PLATFORM_MANUAL.md` / `user-manual.md` 已同步更新 | 人工檢查 diff |

> **關於「部署」**：這個工作環境是雲端沙箱，**無法 SSH 到正式 VPS**（見
> `PLATFORM_MANUAL.md` 第 11 節）。因此本輪自動推進的「部署」定義為：
> ① `npm run build` 產出前端靜態檔、② 後端以正式模式（`NODE_ENV=production`
> 但 `secureCookies` 關閉以便本機 HTTP 測試）在本機啟動、③ 對這組本機「類正式」
> 環境跑 G5、G6。**這不能取代正式站部署**——每個 Sprint 的變更會照常 push、
> 開 PR，但實際上線到 `assess.rong-rise.com` 仍需要你在 VPS 上手動執行
> `CLAUDE.md`／`DEPLOYMENT.md` 的部署指令。每個 Sprint 完成時我會照舊提供
> 那段 VPS 指令。

### 本機驗證環境（G5、G6 共用）

```bash
# 後端：正式模式啟動、資料庫用暫存檔（不動到任何真實資料）
cd server
DB_PATH=/tmp/sprint-verify/db.json JWT_SECRET=sprint-verify-secret \
  ADMIN_EMAIL=admin@verify.local ADMIN_PASSWORD=Verify1234 \
  PORT=4001 NODE_ENV=production node src/server.js &
curl -s localhost:4001/api/health   # 應回 {"ok":true} → G5

# 前端：build 後用 preview 服務靜態檔，模擬正式環境的靜態資源服務
npm run build && npm run preview -- --port 4173
```
每個 Sprint 結束後關閉這兩個背景程序，下一個 Sprint 重新啟動一份乾淨的暫存資料庫，
避免測資跨 Sprint 污染。

### 推進規則

1. 依編號順序（1→2→3→4→5）逐一進行，不並行。
2. 每個 Sprint：實作 → 補測試 → 跑 G1–G6 → 全過才 commit + push（G7）→
   視情況同步文件（G8）→ 記錄驗收結果 → 才開始下一個 Sprint。
3. 若某項功能驗收失敗，先修正並重新跑該 Sprint 的 G1–G6，不允許帶著已知失敗
   項目推進到下一個 Sprint。
4. 待決 backlog（LINE 通知、AI 個人化建議、PostgreSQL 遷移、多租戶、即時告警
   管道）不在目前規劃範圍內，維持「需產品決策後再排入」。Email 通知已於
   Sprint 6 排入，不再屬於待決 backlog（見 Sprint 6 段落與文末待決 Backlog
   表的說明）。

## Sprint 6　監控告警、跨梯次分析與自動化提醒

**背景**：Sprint 3 當時把「Email 通知」列為待決 backlog（見文末），理由是
「需要選定寄信服務、寄件網域設定、費用決策」；VPS 部署驗證時 `npm audit`
也發現後端正式環境相依有 3 個中風險漏洞（已在 Sprint 5 結束後單獨修復並
push，見對應 commit，非本 Sprint 工作項目，這裡僅記錄延續性）。本 Sprint
把「Email 通知」正式從 backlog 排入，同時處理兩項已知維運缺口：深度健康
檢查沒人主動盯、管理者看不到跨班級/跨梯次的趨勢。

**目標**：讓系統壞掉時第一時間有人知道（而不是等學員或教練回報）、讓管理者
能看到「這門課辦了好幾梯，整體是變好還變差」、讓催交從「複製貼上」變成
「按一下真的寄出去」。

### 現況問題
- `GET /api/health?deep=1`（Sprint 5 產出）存在，但沒有任何東西定期呼叫它；
  第二大腦或 OpenRouter 掛掉，要等有人主動發現才知道。
- 管理後台「整體統計」（`AnalyticsTab.jsx`）把**所有班級的所有提交攤平成一張
  總表**，看不出「按班級」的維度，更看不出同一套題庫辦了好幾梯之後，
  平均表現是進步還是退步——這個數字對企業客戶續約/擴大合作最有說服力，
  但目前只有教練層級的「比較梯次」（`CohortCompare.jsx`）且一次只能比較
  自己名下的 2 個班級。
- 催交目前只有「複製提醒訊息」（`ProgressPanel.jsx`）——教練仍要自己貼去
  LINE 或 Email 才會真的送達；系統完全沒有寄信能力（`.env.example` 沒有任何
  SMTP 相關設定）。

### 用戶故事與驗收條件

| # | 故事 | 驗收條件 |
|---|---|---|
| 6.1 | 身為維運者，系統故障時我會主動收到通知，而不用自己去查 | 後端常駐一個內部排程（預設每 5 分鐘，`HEALTH_CHECK_INTERVAL_MINUTES` 可調），呼叫 `deepHealthCheck()`；第二大腦或 OpenRouter 從「正常」變「異常」時寄一封告警信到 `ADMIN_EMAIL`；從「異常」恢復「正常」時也寄一封「已恢復」信。只在**狀態變化**時寄信，不會每次檢查都寄（否則信箱會被灌爆）|
| 6.2 | 身為維運者，重啟服務不會讓我漏收或多收告警 | 上一次已知狀態存進資料庫（新增輕量 collection 或欄位），服務重啟後讀回來繼續比對，不會因為重啟就誤判成「狀態變化」而多寄一次 |
| 6.3 | 身為管理者，我可以看到某套題庫辦過的所有班級，依開課時間排序比較 | 管理後台「整體統計」新增「跨班級／跨梯次」區塊：列出所選題庫底下全部班級（不限特定教練)，每班的作答人數、平均總分、平均達成率、開課日期；沒設定開課日的班排最後並標示「尚未設定開課日」|
| 6.4 | 身為管理者，我可以一眼看出這門課是進步還是退步 | 同一區塊附趨勢圖：X 軸為班級（依開課日排序），Y 軸為平均達成率／風格型題庫改顯示風格分布世代比較（沿用 Sprint 1「不暗示分數高低」的規則）|
| 6.5 | 身為教練，我可以直接寄出催交提醒信，不必自己複製貼上 | 「作答進度」面板新增「寄送提醒信」按鈕：對該班「本階段未完成」的成員逐一寄送個人化提醒信（含班名、階段、報到連結）；同一班 1 小時內只能寄一次（避免誤觸洗版），按鈕在冷卻中顯示剩餘時間 |
| 6.6 | 身為系統管理者，沒設定 SMTP 時其他功能不受影響 | 未設定 SMTP 環境變數時，6.1／6.5 的寄信動作優雅降級（回傳明確錯誤訊息／按鈕顯示「尚未設定寄信服務」），不影響評測本身；比照 `chat.js` 對 `OPENROUTER_API_KEY` 未設定的既有處理模式 |

- **6.3 不需要改後端**：管理後台本來就透過 `GET /api/coach/groups` 拿到全站班級

- **順手修了 Sprint 5 的迴歸**：拆分 `GroupWorkspace` 時漏搬了「作答進度」面板
  （Sprint 4 的催交追蹤），正式站因此看不到這個面板。本 Sprint 補回並加了能抓到

- **順手修了深色模式分頁對比**：分頁列「選取中」膠囊（`bg-white text-brass-600`）在

- **冒煙驗證**：以本機 SMTP 收信器實測——第二大腦斷線/恢復各只收到一封信（約 5 輪檢查
  期間）、重啟服務後不會多寄；催交信只寄給課前未完成者＋待加入者、內容個人化、
  1 小時冷卻生效；跨梯次比較在亮色/深色/手機寬度與 axe 掃描皆正常。

### 設計決策（需產品負責人確認，本輪自動推進採用括號內的預設值）
- **寄信服務**：不綁定特定廠商，採 `nodemailer` + 通用 SMTP 環境變數
  （`SMTP_HOST`／`SMTP_PORT`／`SMTP_USER`／`SMTP_PASS`／`SMTP_FROM`），可接
  Gmail、SendGrid、Mailgun 等任何提供 SMTP relay 的服務（**預設：先用你現有
  的任何一個信箱的 SMTP 設定即可跑起來，之後要換成正式寄件網域/SPF-DKIM
  再換**，這屬於 VPS 端 `.env` 設定，不是程式碼決策，我沒辦法從這裡幫你選
  或申請）。
- **告警管道**：復用同一組寄信機制，寄給 `ADMIN_EMAIL`（**預設：不另外接
  Slack/Discord webhook**；如果之後想要即時性更高的告警管道，可以再開一個
  獨立的 Sprint 補上，不影響本 Sprint 範圍）。
- **催交信 vs LINE**：本 Sprint 只做 Email（**預設：保留「複製提醒訊息」
  按鈕原樣，新按鈕是額外選項而非取代**，LINE 官方帳號整合維持待決 backlog）。
- **跨梯次排序依據**：以 `group.startDate` 排序（**預設**）；管理者若想自訂
  排序（例如依教練分組），列入本 Sprint 結束後的下一輪待辦。

### 冒煙腳本（G6）
1. 手動把 `BRAIN_API_BASE_URL` 指向一個不存在的位址、確認排程跑過一次後
   `ADMIN_EMAIL` 收到「異常」告警信；改回正確位址後收到「已恢復」信。
2. 重啟後端服務，確認**不會**因為重啟就誤發一次多餘的告警信。
3. 管理後台選一套至少有 2 個班級（不同開課日）的題庫，跨班級區塊正確列出
   兩班且依開課日排序；趨勢圖顯示兩個資料點。
4. 教練後台「作答進度」點「寄送提醒信」，未完成成員的信箱各收到一封個人化
   提醒信；1 小時內再按一次，按鈕顯示冷卻中且不會重複寄送。
5. 移除/清空 SMTP 環境變數後重跑，確認 6.1、6.5 都優雅降級、不影響其他
   功能與既有測試。

### 風險
- 寄信是本系統第一次呼叫外部 SMTP 服務，需要在 VPS 上實際驗證：防火牆是否
  擋 SMTP 埠（25/465/587）、寄出的信會不會被收件方判定為垃圾信（沒有
  SPF/DKIM 的情況下，Gmail 等大型信箱有一定機率直接丟垃圾桶）——這部分
  本機沙箱無法完整模擬，需要你在 VPS 部署後實際寄一封測試信確認有沒有
  被擋。
- 內部排程（6.1）是常駐在 Node process 裡的 `setInterval`，systemd 重啟
  服務時排程會跟著重新啟動——這是預期行為，但代表如果服務本身頻繁重啟
  （例如部署腳本每次都重啟），排程的計時會跟著歸零，不是「絕對每 5 分鐘」
  而是「距離上次啟動 5 分鐘」，可接受但值得知道。

## Sprint 7　上線信心與通知擴充

**背景**：Sprint 6 完成後，下一步是**跟產品負責人一起在 VPS 上部署並實測**。回顧

## Sprint 10　題庫內容後台編輯（文字層）

**背景**：產品負責人問「教練能不能客製九大構面？還是要管理者才行？」——現況答案是**都不行**：構面、題目、
評語寫死在 `src/survey/data/assessments/*.js`，教練只能對自己的班挑重點構面與寫備註，管理者只能開關整套題庫
（見 `PLATFORM_MANUAL.md`「修改既有題庫」）。要改一個字就得改程式碼、重新部署。2026-10 與產品負責人確認範圍：
**只開放文字層（不動計分）、只有管理者可編輯、草稿 → 發佈且保留歷史可還原**。

### 範圍
| 可編輯（本 Sprint） | 不可編輯（維持寫在程式碼） |
|---|---|
| 構面名稱、副標；子能力名稱 | 題數、新增／刪除題目、題目順序 |
| 題目文字 | 反向題（`reversed`）、題目所屬構面／子能力 |
| 子能力評語（`COMMENTARY` 的 high／mid／low） | 分數門檻、等級（`LEVELS`）的分數區間與徽章 |
| 落點等級說明文字（`LEVELS` 的 `desc`／`advice`） | 風格型題庫的風格／原型內容（`PROFILES`）、各種 id |

不動計分，所以**已作答資料完全不受影響**：舊紀錄的分數、等級、`result` 快照都不變。唯一的外觀差異是
報告在檢視時引用設定文字的地方（題目、評語、等級說明）會顯示目前發佈的版本。

### 設計
- **覆寫層，不是搬進資料庫**：程式碼裡的題庫仍是基準（預設值）；資料庫只存「管理者改過的欄位」。
  好處：沒有覆寫就跟現在完全一樣、回滾只要清掉覆寫、不必遷移任何既有資料。
- **儲存**：新增 `assessmentContent` collection，每個題庫一筆：`draft`（草稿覆寫與更新時間）、
  `published`（目前生效的覆寫、版本號、發佈時間／人／備註）、`history`（歷次發佈，最多 20 筆）。
- **覆寫格式**（只接受白名單欄位）：
  `{ dimensions: {id: {name, subtitle}}, subDimensions: {id: {name}}, questions: {id: text},
  commentary: {subId: {high, mid, low}}, levels: {id: {desc, advice}} }`；
  伺服器只驗形狀、key 格式與字數上限（它不知道前端題庫有哪些 id），前端套用時忽略不認得的 id。
- **前端套用**：`AppShell` 載入後取 `GET /api/assessments/content`，在**就地修改**題庫設定物件的可編輯欄位
  （`ALL_QUESTIONS`、`COMMENTARY`、`LEVELS` 都與 `DIMENSIONS` 共用同一批物件，改一處全站一致），
  先存一份原始快照以便重新套用／還原。取不到就用程式碼內建版本，不擋畫面。
- **管理後台新分頁「題庫內容」**：選題庫 → 依構面展開編輯；每個欄位顯示「內建原文」與「已修改」標記、
  可單欄還原；儲存草稿 → 預覽（只在管理者自己的畫面套用，頂端有橫幅）→ 發佈（填備註、二次確認）→ 歷史
  清單可還原到任一版（還原也是一次新的發佈，歷史不會被改寫）。
- **權限與稽核**：寫入一律 `requireAdmin`；教練與學員只能讀已發佈版本；發佈／還原寫入稽核日誌。

### 工作項目與驗收條件
| # | 項目 | 驗收條件 |
|---|---|---|
| 10.1 | 後端：覆寫資料與 API | `assessmentContent` collection；`GET /api/assessments/content`（登入即可，只回已發佈）；管理者 `GET/PUT draft`、`POST publish`、`POST rollback`、`DELETE draft`；非管理者寫入 403、未登入 401；白名單／字數上限驗證；歷史保留 20 筆；發佈與還原寫稽核日誌；後端測試涵蓋以上與「草稿不影響已發佈」 |

- 範圍：**只改文字、不動計分**。要增刪題目、改反向題或分數門檻，仍視為「新版本題庫」（見 `PLATFORM_MANUAL.md`），之後另立 Sprint。
- 權限：**只有管理者**。教練維持現有的班級層級設定（重點構面、構面備註）。

### 已知取捨（先寫下來，驗收時要確認有被處理或明講）
- 學員**已送出的 `result` 快照**裡存的構面名稱等字樣不會被追溯修改；因此同一份舊報告裡，「從快照讀」的字樣
  與「從設定讀」的字樣可能新舊並存。實作時要逐一找出報告中哪些字從哪裡來，並在文件寫明，不要讓它在畫面上自相矛盾。
- 覆寫在前端套用，**第一次載入有一瞬間可能先閃過內建文字**。作法：AppShell 等覆寫載入（有逾時上限）再渲染路由。
- 伺服器不知道題庫有哪些 id，無法擋掉「指向不存在 id」的覆寫；由前端編輯器只提供已知 id、套用時忽略未知 id 來保證。

逐處確認新文字出現；還原後逐處確認恢復；檢查舊作答的分數與等級完全沒變。

- **10.1–10.5 如規劃完成**：後端 `assessmentContent` 與六支 API、前端套用層、管理後台「題庫內容」分頁（含預覽、發佈、歷史還原）、
  端對端測試、文件。後端測試 125 → 142、前端 271 → 300，新增 1 條 E2E。
- **規劃時列為「已知取捨」的那一條，實作時證實是真的問題，而且比預期嚴重**：舊作答的 `result` 快照裡存著當時的構面／副標／
  子能力名稱與等級說明，報告直接讀快照，而評語是從目前設定讀——所以改完之後**同一份舊報告會名稱是舊的、評語是新的**，
  而且「改錯字」這個最常見的用途也傳不到既有報告，功能會大打折扣。解法：`api/client.js` 對每個 API 回應呼叫
  `refreshResultsInPlace()`，以 id 對應、用目前文字換掉這些顯示用字（只換文字，分數與等級 id 不動）；
  E2E 用「改文字前就送出的舊作答」證明舊報告的構面名稱會更新。
- **風格型題庫的等級說明不開放**：DISC／識己® 的 `LEVELS` 是從 `PROFILES` 衍生的副本，改副本不會影響實際顯示的風格說明，
  只會造成不一致；套用層與編輯器都排除它們，並有測試。
- **管理後台頁面不隨 `contentVersion` 重掛**：一開始把版本號放進整個路由區塊的 key，預覽一按編輯器就被重掛、未儲存的編輯全掉；
  改成管理後台例外，並另外把未存檔編輯暫存在 `sessionStorage`（換分頁、換題庫、重新整理都還在）。
- **視覺檢查抓到兩個問題**：①副標欄位標成「英文名稱」但內容是中文；②群組標題用 `<fieldset>`／`<legend>`，邊框線穿過標題文字
  （深色模式最明顯）——跟 Sprint 9 在作答頁修的是同一類問題，改用 `div role="group"`。
- **反向題的風險只能提示、不能擋**：編輯器在反向題上標「反向題」並在區段頂端說明必須維持反向語意；系統無法判斷一句話是正向還是反向，
  這項風險寫進使用手冊與文件。
- **尚未做**：覆寫的歷史只存最近 20 筆；沒有「差異對照」畫面（只在單欄顯示內建原文）；多位管理者同時編輯同一題庫時，
  後存的會覆蓋先存的草稿（沒有衝突偵測）——目前使用規模（單一管理者）可接受，列入已知限制。

## Sprint 11　教練後台、管理者權限與填答流程 UX

**背景**：2026-10 部署 Sprint 9–10 後，產品負責人要求針對教練後台、管理者權限設定與填答者流程再做一輪 UX 優化。

### 走查發現（依影響排序）
**教練後台**
- **隱私**：`GET /api/coach/directory` 回傳全站所有非管理者用戶的姓名與 Email 給任何教練；「成員管理」是一個約 5 行高、
  沒有搜尋的小框，一次列出全站所有人。用戶一多找不到人，也等於任何教練都能翻閱別班學員的 Email。

## Sprint 12　隱私權政策與註冊同意

**背景**：Sprint 11 做完權限與名單隱私後，盤點資料處理現況，發現：沒有隱私權政策與服務條款、註冊時沒有任何同意；
FAQ「資料安全與隱私」只寫「只有你、教練、管理者看得到成績」，沒提到 **AI 小幫手會把學員的評測結果摘要與對話內容傳給第三方 AI 服務
（OpenRouter）**、寄信會經過 SMTP 服務商、延伸閱讀會對外查詢，也沒提到「他評對被評者匿名，但教練與管理者看得到評分者身分」。
正式對企業客戶使用前通常會被問到，台灣個資法也要求告知蒐集目的與類別。2026-10 與產品負責人確認本 Sprint 只做
**「隱私權政策＋註冊同意」**；匯出／刪除自己的資料、AI 小幫手可關閉、班級加入通知先不做（已決定將來刪除採「匿名化、保留班級統計」）。

### 設計
- **政策內容以實際程式行為為準**：每一條都對照程式確認（蒐集哪些欄位、誰看得到、送出什麼給第三方、cookie／localStorage 用途、備份保留），不寫做不到的承諾（例如目前**沒有**自助刪除與自動清除機制，就如實寫「請聯絡窗口申請」）。
- **草稿標記**：經營者名稱與聯絡信箱由產品負責人之後自己填（`src/survey/legal/policy.js`）。沒填完或 `status !== 'published'` 時，兩個頁面頂端顯示明顯的「草稿，尚待確認」，
  欄位以醒目的待填標記呈現——不會有編造的公司名稱或信箱上線。法律文字需由負責人或法務確認後才改成 `published`。
- **同意要記錄、要可追溯**：使用者資料新增 `consent: { version, acceptedAt }`；政策有實質修改時調高 `POLICY_VERSION`，所有人下次登入會再被詢問一次。
- **伺服器端強制**：註冊 API 沒帶 `acceptPolicy: true` 回 400（不能只靠前端勾選框）；前後端版本號各存一份，用測試保證兩邊一致。
- **既有用戶**：沒有同意紀錄的人，登入後出現一次「請閱讀並同意」的畫面（同意後才能使用；不同意可登出）。**這會在部署後影響所有現有用戶一次**，部署清單已加註提醒。
