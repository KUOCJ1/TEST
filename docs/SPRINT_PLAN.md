## 驗證標準與推進機制

每個 Sprint 是否「完成、可以往下一個推進」，一律用以下**共同關卡（Gate）**加上
該 Sprint 自己的**功能驗收表**共同判定。兩者都通過才算過關；任一項不過，
該 Sprint 視為未完成，不推進到下一個。

### 共同關卡（每個 Sprint 都要過，缺一不可）

| # | 檢查 | 通過標準 | 指令 |
|---|---|---|---|
| G1 | 前端單元/元件測試 | 全綠，且新增/變更的行為有對應測試（不是只維持原有測試通過） | `npm test` |
| G2 | 後端 API 測試 | 全綠 | `cd server && npm test` |
| G3 | Lint | 0 problems | `npm run lint` |
| G4 | Production build | 成功產出 `dist/`，無 build 期錯誤 | `npm run build` |
| G5 | 後端可正常啟動並回應健康檢查 | `{"ok":true}` | 見下方「本機驗證環境」 |
| G6 | 冒煙測試（Smoke） | 該 Sprint 涉及的畫面至少手動或以 Playwright 跑過一次黃金路徑，無 console error、無明顯版面錯亂（含手機寬度 375px 與深色模式各看一次） | 見各 Sprint 的「冒煙腳本」 |
| G7 | Git 狀態 | 變更已 commit 並 `git push` 到 `claude/ai-assessment-survey-4vhjun`；GitHub Actions `deploy.yml` 綠燈 | `git push` + 確認 PR #7 的 check run 狀態 |
| G8 | 文件同步 | 若該 Sprint 影響架構、API 或使用者操作流程，`PLATFORM_MANUAL.md` / `user-manual.md` 已同步更新 | 人工檢查 diff |

> **關於「部署」**：這個工作環境是雲端沙箱，**無法 SSH 到正式 VPS**（見
> `PLATFORM_MANUAL.md` 第 11 節）。因此本輪自動推進的「部署」定義為：
> ① `npm run build` 產出前端靜態檔、② 後端以正式模式（`NODE_ENV=production`
> 但 `secureCookies` 關閉以便本機 HTTP 測試）在本機啟動、③ 對這組本機「類正式」
> 環境跑 G5、G6。**這不能取代正式站部署**——每個 Sprint 的變更會照常 push、
> 開 PR，但實際上線到 `assess.rong-rise.com` 仍需要你在 VPS 上手動執行
> `CLAUDE.md`／`DEPLOYMENT.md` 的部署指令。每個 Sprint 完成時我會照舊提供
> 那段 VPS 指令。

### 本機驗證環境（G5、G6 共用）

```bash
# 後端：正式模式啟動、資料庫用暫存檔（不動到任何真實資料）
cd server
DB_PATH=/tmp/sprint-verify/db.json JWT_SECRET=sprint-verify-secret \
  ADMIN_EMAIL=admin@verify.local ADMIN_PASSWORD=Verify1234 \
  PORT=4001 NODE_ENV=production node src/server.js &
curl -s localhost:4001/api/health   # 應回 {"ok":true} → G5

# 前端：build 後用 preview 服務靜態檔，模擬正式環境的靜態資源服務
npm run build && npm run preview -- --port 4173
```
每個 Sprint 結束後關閉這兩個背景程序，下一個 Sprint 重新啟動一份乾淨的暫存資料庫，
避免測資跨 Sprint 污染。

### 推進規則

1. 依編號順序（1→2→3→4→5）逐一進行，不並行。
2. 每個 Sprint：實作 → 補測試 → 跑 G1–G6 → 全過才 commit + push（G7）→
   視情況同步文件（G8）→ 記錄驗收結果 → 才開始下一個 Sprint。
3. 若某項功能驗收失敗，先修正並重新跑該 Sprint 的 G1–G6，不允許帶著已知失敗
   項目推進到下一個 Sprint。
4. 待決 backlog（LINE 通知、AI 個人化建議、PostgreSQL 遷移、多租戶、即時告警
   管道）不在目前規劃範圍內，維持「需產品決策後再排入」。Email 通知已於
   Sprint 6 排入，不再屬於待決 backlog（見 Sprint 6 段落與文末待決 Backlog
   表的說明）。

## Sprint 1　報告正確性與作答體驗

**目標**：DISC／識己® 這類「風格輪廓型」題庫的所有畫面都不再出現「分數越高
越好」的錯誤暗示；長問卷的作答體驗與效度提升。

### 現況問題

1. **風格型題庫在「我的分析」頁仍用總分做比較**（`dashboard/UserDashboard.jsx`）：
   「學習增益」區塊顯示「課前總分 → 課後總分、整體增益 +N」，「歷次總分趨勢」
   圖也畫總分，「構面進步追蹤」把構面變化標成綠色↑/紅色↓。對 `PROFILE_MODE`
   題庫而言總分沒有意義，構面升降也不是「進步／退步」，而是「風格位移」。
2. **目標面板把最低分風格標成「最待強化」**（`components/GoalPanel.jsx` 使用
   `result.weakest`）：對 DISC 來說，最低分的風格不是缺點。
3. **作答時公開標示反向題**（`components/QuestionCard.jsx` 顯示 🔄 圖示，
   `SurveyApp.jsx` 開頭也提示「標示題目為反向計分」）：反向題的目的是偵測
   「不看題目一律勾高分」的作答傾向，事先告訴受測者哪幾題是反向，等於讓
   這個機制失效，是心理計量上的效度問題。
4. **360° 他評提示文字寫死「領導力行為表現」**（`SurveyApp.jsx`）：評 DISC
   時語意不符。
5. **L9D 90 題一次攤在同一頁**：長問卷完成率與作答品質都會隨疲勞下降。

### 用戶故事與驗收條件

| # | 故事 | 驗收條件 |
|---|---|---|
| 1.1 | 身為 DISC／識己® 學員，我在「我的分析」看到的是**風格變化**而非「進步退步」 | `PROFILE_MODE` 時：隱藏總分增益卡與總分趨勢圖；改顯示「風格變化」卡（課前主要/次要風格 → 課後主要/次要風格，各構面位移用中性色 ←→ 呈現，不用綠紅）|
| 1.2 | 身為風格型題庫學員，目標面板用中性說法引導我 | `PROFILE_MODE` 時文案改為「想刻意練習哪一種風格？」，並可自選構面，而非預設最低分構面 |
| 1.3 | 身為受測者，我看不出哪些題目是反向題 | 作答頁移除反向題標示與說明文字；**計分邏輯不變**；報告／教練端仍可檢視題目設定 |
| 1.4 | 身為 360° 評分者，提示文字符合我正在填的題庫 | 他評提示改從題庫設定讀取（例如新增 `RATER_PROMPT` 欄位，未設定時用中性預設「的日常行為表現」）|
| 1.5 | 身為 L9D 學員，我可以一段一段作答 | 以構面分頁（上一段／下一段），頂部顯示「第 3 / 9 段」與各段完成狀態；最後一段才出現送出鈕；草稿自動儲存機制沿用；題數 ≤ 40 的題庫可維持單頁 |
| 1.6 | 身為學員，我可以用鍵盤快速作答 | 題目聚焦時按 1–5 直接選分並自動跳下一題；符合無障礙焦點樣式 |

### 主要修改檔案
`dashboard/UserDashboard.jsx`、`components/GoalPanel.jsx`、`components/QuestionCard.jsx`、
`SurveyApp.jsx`、`data/assessments/*.js`（`RATER_PROMPT`）、`components/JourneyTimeline.jsx`（確認敘事不引用總分）、
對應測試 `src/test/*`。

### 冒煙腳本（G6）
1. 以 DISC 帳號登入 → 作答並提交 → 「我的分析」：確認**沒有**總分增益卡／總分趨勢圖，改看到「風格變化」卡，構面位移不是綠紅配色。
2. 同一帳號在目標面板新增目標：文案為中性引導語，非「最待強化」。
3. 進 L9D 作答頁：確認題目旁**沒有** 🔄 反向題圖示，且分段導覽（第 N / 9 段）正常運作，跳到未答題會定位到正確分頁。
4. 在 DISC 的 360° 他評頁確認提示文字不是「領導力行為表現」。
5. 手機寬度（375px）與深色模式下重複步驟 1、3，畫面無跑版。

### 風險
- 分頁作答需確保「未答題標紅並跳轉」在跨頁時仍正確（跳到該題所在分頁）。
- 移除反向題標示後，舊版 PDF 手冊若有截圖需一併更新。

## Sprint 2　學員首頁「下一步」導引

**目標**：學員登入後的第一個畫面直接告訴他「現在該做什麼」，而不是一排題庫卡片讓他自己判斷。

### 現況問題
- `/home`（`AppShell.jsx` 的 `AssessmentHome`）只列出題庫卡片，學員要自己判斷該做課前、課後、還是 360°。
- 所屬班級的狀態（開放日期、目前階段、還差幾人他評）散落在不同頁面。
- 評完測之後，學員沒有「回來的理由」——首頁沒有顯示目標進度或推薦內容。

### 用戶故事與驗收條件

| # | 故事 | 驗收條件 |
|---|---|---|
| 2.1 | 身為學員，首頁最上方有一張「下一步」卡片 | 依優先序顯示一個主要行動：①所屬班級課前未作答 →「開始課前評測」②課前已完成、班級已進入課後 →「開始課後複測」③360° 他評邀請未完成 →「還有 N 位同事等你評分」④都完成 →「看看你的成長報告」|
| 2.2 | 身為班級學員，我看得到我的班級狀態 | 班級資訊條：班名、教練、目前階段（課前／課後）、課後開放日期倒數 |
| 2.3 | 身為學員，我在首頁看到目標進度 | 「我的目標」摘要：進行中目標數、行動完成率，點擊跳到分析頁目標區 |
| 2.4 | 身為學員，題庫卡片顯示清楚的狀態標籤 | 每張卡片顯示「未作答／課前已完成／課後已完成／可重測」與最近作答日期 |
| 2.5 | 身為首次登入學員，有 3 步驟快速導覽 | 取代現有 `OnboardingBanner` 的一次性說明，可關閉並記住（`localStorage`，失敗時不影響使用）|

### 主要修改檔案
`AppShell.jsx`（抽出 `AssessmentHome` 至 `home/HomePage.jsx`）、`components/AssessmentCard.jsx`、
`components/OnboardingBanner.jsx`、`api/client.js`；後端視需要新增 `GET /api/me/summary`
（一次回傳班級、階段、待評 360°、目標統計，避免首頁打 5 支 API）。

### 冒煙腳本（G6）
1. 尚未作答的學員登入 →`/home` 最上方出現「下一步」卡片，指向「開始課前評測」。
2. 完成課前、班級切到課後階段後重新整理 →「下一步」卡片改為「開始課後複測」。
3. 有待評 360° 邀請的學員登入 → 卡片顯示「還有 N 位同事等你評分」，點擊導向 360° 頁。
4. 題庫卡片檢查狀態標籤（未作答／課前已完成／課後已完成／可重測）與最近作答日期正確。
5. 首次登入帳號看到 3 步驟導覽，關閉後重新整理不再出現。
6. 手機寬度與深色模式下重複步驟 1。

### 風險
- 「下一步」判斷邏輯需與 `SurveyApp.jsx` 的課前/課後自動判定**共用同一個函式**，避免兩處邏輯不一致。

## Sprint 3　學習閉環：目標 × 延伸閱讀 × 複測

**目標**：把目前各自獨立的「延伸閱讀」「發展目標」「課後複測」串成一條學習路徑：
**診斷 → 選主題 → 讀 → 做 → 再測**。

### 現況問題
- 延伸閱讀（`components/LearningResources.jsx`）點出去就結束，平台不知道學員讀了什麼。
- 發展目標（`GoalPanel.jsx`）與延伸閱讀沒有關聯，行動項目要學員自己想。
- 沒有任何機制提醒學員「目標設定後 N 週，該回來複測看看有沒有改變」。

### 用戶故事與驗收條件

| # | 故事 | 驗收條件 |
|---|---|---|
| 3.1 | 身為學員，我可以把文章加入「我的學習清單」 | 延伸閱讀每篇文章有「加入清單」按鈕；清單存於後端（新增 `readingList` collection 或併入 `goals`）；可標記「已讀」|
| 3.2 | 身為學員，我可以把一篇文章直接變成目標的行動項目 | 「加入目標」→ 選擇既有目標或新建，行動文字預填「閱讀：〈文章標題〉」並附連結 |
| 3.3 | 身為學員，我有一頁「我的學習」 | 新分頁（或分析頁子區塊）彙整：進行中目標、學習清單（未讀／已讀）、下次建議複測日期 |
| 3.4 | 身為學員，系統建議我何時複測 | 目標建立時可設定「預計檢視日」（預設 4 週後）；到期後首頁「下一步」卡片（Sprint 2）提示「回來複測，看看 ○○ 有沒有改變」|
| 3.5 | 身為學員，複測後我看得到目標構面的變化 | 分析頁目標卡片顯示「設定目標時該構面分數 → 最新分數」（風格型題庫用中性呈現，沿用 Sprint 1 規則）|
| 3.6 | 身為管理者，我看得到延伸閱讀的使用情形 | 管理後台統計：各構面文章點擊數、加入清單數（僅彙總數據，不揭露個人閱讀紀錄）|

### 主要修改檔案
`components/LearningResources.jsx`、`components/GoalPanel.jsx`、新增 `learning/MyLearningPage.jsx`、
`server/src/routes/goals.js`（或新增 `readingList.js`）、`server/src/db.js`（`COLLECTIONS` 加新 collection）、
`admin/AnalyticsTab.jsx`。

### 設計決策（需產品負責人確認，本輪自動推進採用括號內的預設值）
- **閱讀紀錄的隱私**：比照目標的設計（「只有你看得到」）（**預設：教練看不到**，之後如需開放「分享給教練」再加開關）。
- **提醒管道**：本 Sprint 只做**站內提醒**（首頁卡片）。Email 提醒需要 SMTP 服務與寄件網域設定，列入待決 backlog（見文末）。

### 冒煙腳本（G6）
1. 學員在延伸閱讀點「加入清單」→ 進「我的學習」頁看到該篇、狀態未讀；標記已讀後狀態更新。
2. 從一篇文章「加入目標」→ 建立新目標，行動項目預填「閱讀：〈標題〉」與連結。
3. 建立目標時設定預計檢視日為過去日期（測試用）→「下一步」卡片出現複測提醒。
4. 有課前/課後兩筆資料且該構面設有目標的帳號 → 目標卡片顯示「設定時分數 → 最新分數」。
5. 管理後台看得到延伸閱讀點擊數／加入清單數彙總（非個人明細）。

## Sprint 4　教練工作台強化

**目標**：讓教練在開課前、課中、課後三個時間點都能快速掌握班級狀態，並大幅
減少撰寫評語的時間。

### 現況問題
- 教練要自己比對成員名單才知道誰還沒交；沒有「一鍵催交」的輔助。
- 班級報告有落點分布與整體評語，但沒有**班級層級的課前 → 課後學習成效**（這是
  對企業客戶交付成果最有說服力的數字）。
- 評語從空白開始寫，同一個班常要重複寫類似內容。

### 用戶故事與驗收條件

| # | 故事 | 驗收條件 |
|---|---|---|
| 4.1 | 身為教練，我一眼看到誰還沒作答 | 班級頁「作答進度」：課前 x/N、課後 y/N，未完成者列表（姓名、Email、加入日期）|

## Sprint 6　監控告警、跨梯次分析與自動化提醒

**背景**：Sprint 3 當時把「Email 通知」列為待決 backlog（見文末），理由是
「需要選定寄信服務、寄件網域設定、費用決策」；VPS 部署驗證時 `npm audit`
也發現後端正式環境相依有 3 個中風險漏洞（已在 Sprint 5 結束後單獨修復並
push，見對應 commit，非本 Sprint 工作項目，這裡僅記錄延續性）。本 Sprint
把「Email 通知」正式從 backlog 排入，同時處理兩項已知維運缺口：深度健康
檢查沒人主動盯、管理者看不到跨班級/跨梯次的趨勢。

**目標**：讓系統壞掉時第一時間有人知道（而不是等學員或教練回報）、讓管理者
能看到「這門課辦了好幾梯，整體是變好還變差」、讓催交從「複製貼上」變成
「按一下真的寄出去」。

### 現況問題
- `GET /api/health?deep=1`（Sprint 5 產出）存在，但沒有任何東西定期呼叫它；
  第二大腦或 OpenRouter 掛掉，要等有人主動發現才知道。
- 管理後台「整體統計」（`AnalyticsTab.jsx`）把**所有班級的所有提交攤平成一張
  總表**，看不出「按班級」的維度，更看不出同一套題庫辦了好幾梯之後，
  平均表現是進步還是退步——這個數字對企業客戶續約/擴大合作最有說服力，
  但目前只有教練層級的「比較梯次」（`CohortCompare.jsx`）且一次只能比較
  自己名下的 2 個班級。
- 催交目前只有「複製提醒訊息」（`ProgressPanel.jsx`）——教練仍要自己貼去
  LINE 或 Email 才會真的送達；系統完全沒有寄信能力（`.env.example` 沒有任何
  SMTP 相關設定）。

### 用戶故事與驗收條件

| # | 故事 | 驗收條件 |
|---|---|---|
| 6.1 | 身為維運者，系統故障時我會主動收到通知，而不用自己去查 | 後端常駐一個內部排程（預設每 5 分鐘，`HEALTH_CHECK_INTERVAL_MINUTES` 可調），呼叫 `deepHealthCheck()`；第二大腦或 OpenRouter 從「正常」變「異常」時寄一封告警信到 `ADMIN_EMAIL`；從「異常」恢復「正常」時也寄一封「已恢復」信。只在**狀態變化**時寄信，不會每次檢查都寄（否則信箱會被灌爆）|
| 6.2 | 身為維運者，重啟服務不會讓我漏收或多收告警 | 上一次已知狀態存進資料庫（新增輕量 collection 或欄位），服務重啟後讀回來繼續比對，不會因為重啟就誤判成「狀態變化」而多寄一次 |
| 6.3 | 身為管理者，我可以看到某套題庫辦過的所有班級，依開課時間排序比較 | 管理後台「整體統計」新增「跨班級／跨梯次」區塊：列出所選題庫底下全部班級（不限特定教練)，每班的作答人數、平均總分、平均達成率、開課日期；沒設定開課日的班排最後並標示「尚未設定開課日」|
| 6.4 | 身為管理者，我可以一眼看出這門課是進步還是退步 | 同一區塊附趨勢圖：X 軸為班級（依開課日排序），Y 軸為平均達成率／風格型題庫改顯示風格分布世代比較（沿用 Sprint 1「不暗示分數高低」的規則）|

### 設計決策（需產品負責人確認，本輪自動推進採用括號內的預設值）
- **寄信服務**：不綁定特定廠商，採 `nodemailer` + 通用 SMTP 環境變數
  （`SMTP_HOST`／`SMTP_PORT`／`SMTP_USER`／`SMTP_PASS`／`SMTP_FROM`），可接
  Gmail、SendGrid、Mailgun 等任何提供 SMTP relay 的服務（**預設：先用你現有
  的任何一個信箱的 SMTP 設定即可跑起來，之後要換成正式寄件網域/SPF-DKIM
  再換**，這屬於 VPS 端 `.env` 設定，不是程式碼決策，我沒辦法從這裡幫你選
  或申請）。
- **告警管道**：復用同一組寄信機制，寄給 `ADMIN_EMAIL`（**預設：不另外接
  Slack/Discord webhook**；如果之後想要即時性更高的告警管道，可以再開一個
  獨立的 Sprint 補上，不影響本 Sprint 範圍）。
- **催交信 vs LINE**：本 Sprint 只做 Email（**預設：保留「複製提醒訊息」
  按鈕原樣，新按鈕是額外選項而非取代**，LINE 官方帳號整合維持待決 backlog）。
- **跨梯次排序依據**：以 `group.startDate` 排序（**預設**）；管理者若想自訂
  排序（例如依教練分組），列入本 Sprint 結束後的下一輪待辦。

### 冒煙腳本（G6）
1. 手動把 `BRAIN_API_BASE_URL` 指向一個不存在的位址、確認排程跑過一次後
   `ADMIN_EMAIL` 收到「異常」告警信；改回正確位址後收到「已恢復」信。
2. 重啟後端服務，確認**不會**因為重啟就誤發一次多餘的告警信。
3. 管理後台選一套至少有 2 個班級（不同開課日）的題庫，跨班級區塊正確列出
   兩班且依開課日排序；趨勢圖顯示兩個資料點。
4. 教練後台「作答進度」點「寄送提醒信」，未完成成員的信箱各收到一封個人化
   提醒信；1 小時內再按一次，按鈕顯示冷卻中且不會重複寄送。
5. 移除/清空 SMTP 環境變數後重跑，確認 6.1、6.5 都優雅降級、不影響其他
   功能與既有測試。

### 風險
- 寄信是本系統第一次呼叫外部 SMTP 服務，需要在 VPS 上實際驗證：防火牆是否
  擋 SMTP 埠（25/465/587）、寄出的信會不會被收件方判定為垃圾信（沒有
  SPF/DKIM 的情況下，Gmail 等大型信箱有一定機率直接丟垃圾桶）——這部分
  本機沙箱無法完整模擬，需要你在 VPS 部署後實際寄一封測試信確認有沒有
  被擋。
- 內部排程（6.1）是常駐在 Node process 裡的 `setInterval`，systemd 重啟
  服務時排程會跟著重新啟動——這是預期行為，但代表如果服務本身頻繁重啟
  （例如部署腳本每次都重啟），排程的計時會跟著歸零，不是「絕對每 5 分鐘」
  而是「距離上次啟動 5 分鐘」，可接受但值得知道。
